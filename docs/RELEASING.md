# Releasing

## Current candidate: 0.10.0

The source version and bundle build are `0.10.0` / `24`. [Release notes](releases/v0.10.0.md) and an [evidence checklist](releases/v0.10.0-checklist.md) are prepared. This does not mean that signing, notarization, interactive Mac tests, or publication have completed. Record their actual results in the checklist; do not infer them from ordinary CI.

## Prepare a signed draft in GitHub Actions

This route requires an active Apple Developer Program membership, a **Developer ID Application** certificate with its private key, and a notarytool-compatible App Store Connect API key. These credentials cannot be generated by the build or replaced by ad-hoc signing.

In [repository Settings → Secrets and variables → Actions](https://github.com/nbr41to/cmd-kana/settings/secrets/actions), configure these repository secrets. Enter the values in GitHub; do not paste private keys or passwords into Issues or chat.

| Secret | Value |
| --- | --- |
| `MACOS_CERTIFICATE_BASE64` | Base64-encoded `.p12` exported from Keychain Access, including the Developer ID Application certificate and private key. |
| `MACOS_CERTIFICATE_PASSWORD` | The password used to encrypt that `.p12`. Use a nonempty password. |
| `CODESIGN_IDENTITY` | Full identity name, such as `Developer ID Application: Your Name (TEAMID)`. |
| `APPLE_API_KEY_BASE64` | Base64-encoded App Store Connect `.p8` API private key. |
| `APPLE_API_KEY_ID` | The API key ID. |
| `APPLE_API_ISSUER_ID` | The issuer ID associated with the API key. |

On a Mac, `base64 -i /path/to/certificate.p12 | pbcopy` copies an encoded certificate for the corresponding secret; use the same command with the `.p8` path for the API key. Keep the original exports private and clear clipboard contents after setup.

Open [Actions → Prepare notarized release](https://github.com/nbr41to/cmd-kana/actions/workflows/release.yml), choose **Run workflow**, and select `main`.

The workflow:

1. Validates matching versions, release notes, and an Apple Silicon runner.
2. Runs the full release gate without exposing signing credentials to ordinary PR builds.
3. Imports the signing identity and notary credentials into a temporary keychain.
4. Builds with a macOS 11.0 deployment target, signs with the hardened runtime, submits to Apple, and staples the ticket.
5. Verifies the extracted distribution ZIP's checksum, metadata, architecture, executable minimum OS, Developer ID signature, notarization ticket, and Gatekeeper assessment.
6. Uploads the verified ZIP and checksum, then creates a **draft** GitHub Release pointing at that exact source commit. It does not overwrite an existing Release or publish the draft automatically.
7. Deletes the temporary keychain and key exports, including when an earlier step fails.

Download and test the notarized ZIP using [the candidate checklist](releases/v0.10.0-checklist.md). Once those checks pass and their evidence is recorded, publish the draft from GitHub Releases. This interactive validation is a release requirement; producing a signed ZIP is not evidence of IME or update behavior.

## 1. Prepare

1. Move completed entries from `Unreleased` in `CHANGELOG.md` to the new version.
2. Keep the versions in `Cargo.toml` and `app/Info.plist` identical.
3. Increment `CFBundleVersion` in `app/Info.plist`.
4. Run `./scripts/check.sh` and complete the manual matrix in `docs/TESTING.md`.
5. Run `python3 scripts/check-release.py` to check `Cargo.toml`, `Cargo.lock`, the bundle, the changelog, and versioned release documents.

## 2. Create an internal release candidate

```sh
./scripts/archive.sh
```

This produces an ad-hoc-signed ZIP and SHA-256 checksum under `target/dist`. It is for testing, not the preferred public download.

Pushing a matching tag such as `v0.7.1` runs the release-candidate workflow. The workflow deliberately does not publish a GitHub Release, preventing accidental distribution of an unnotarized build.

## 3. Sign and notarize a public build

Create a notarytool keychain profile once, then run:

```sh
export CODESIGN_IDENTITY='Developer ID Application: Example (TEAMID)'
export NOTARY_PROFILE='cmd-kana-notary'
./scripts/notarize.sh
```

The script signs with the hardened runtime, submits the app to Apple, staples and validates the ticket, assesses it with Gatekeeper, and creates a final ZIP plus checksum.

It then runs `scripts/verify-public-release.sh` against the actual final ZIP, including a fresh extraction. The script rejects ad-hoc signing. SHA-256 files contain a relative filename, so `shasum -a 256 -c cmd-kana-VERSION-macos-notarized.zip.sha256` works from the download directory. Python 3 is needed for release metadata and minimum-OS validation.

## 4. Publish

1. Verify the checksum on a second machine.
2. Install and run the notarized ZIP in a clean macOS account.
3. Create release notes from `CHANGELOG.md`, including known limitations and the manual test matrix.
4. Upload only the `-notarized.zip` and its `.sha256` file.
5. Keep the previous release available for rollback.

For a locally signed and verified build, a draft can be created from the Mac using GitHub CLI:

```sh
version=$(python3 scripts/check-release.py --version-only)
./scripts/verify-public-release.sh
gh release create "v$version" \
  "target/dist/cmd-kana-$version-macos-notarized.zip" \
  "target/dist/cmd-kana-$version-macos-notarized.zip.sha256" \
  --repo nbr41to/cmd-kana --target "$(git rev-parse HEAD)" --draft \
  --title "cmd-kana $version" --notes-file "docs/releases/v$version.md"
```

Push the source commit first and verify its CI results. Complete the candidate checklist before publishing the draft. Then update the README's distribution status and verify the public download path. Preparing a draft alone does not make it available to the in-app updater.

### In-app update assets

The updater uses GitHub's latest **published stable Release**, not commits or tags alone. Publish a tag named `vMAJOR.MINOR.PATCH` (or `MAJOR.MINOR.PATCH`) and attach:

- `cmd-kana-MAJOR.MINOR.PATCH-macos-notarized.zip`
- `cmd-kana-MAJOR.MINOR.PATCH-macos-notarized.zip.sha256`

These are the existing `scripts/notarize.sh` outputs. The updater also recognizes the corresponding `-macos.zip` and `.zip.sha256` names from `scripts/archive.sh` for internal testing; keep public builds signed and notarized as described above. The notarized ZIP takes precedence when both exist. Each ZIP must be at most 100 MiB and contain only the `cmd-kana.app` tree, without AppleDouble metadata. The app uses GitHub's SHA-256 asset digest when available and otherwise downloads the matching checksum file.

The bundled version must exactly match the tag, without its optional `v` prefix. The app must retain its bundle identifier and satisfy the installed app's designated signing requirement. Each replacement must include the updater's `--update-complete` startup acknowledgment, which is sent automatically once Cocoa finishes launching.

Upload assets to a draft Release first, then publish it after verification so users do not see a partially uploaded update. The current release-candidate workflow does not publish a Release automatically. A repository with no published Release is reported as having no distribution available, not as being up to date.

## Rollback

If a regression is found, mark the release as affected, restore the previous notarized artifact, and issue a patch version. Do not reuse or move an existing version tag.
